# Unstick the horror deck, then fill the night

The six fix batches mostly landed as intended. Save sanitizing, never-delete loading, the collider build queue, Rapier aim rays, the all-air chunk skip, the pause gain, the horror phase machine, the post-processing stack and key remapping all check out in the code. They also introduced **five new bugs that should be fixed before anything else**: two flora materials share one shader by accident, the lazy audio loading breaks the horror "memory" event, an abandoned key-remap prompt can steal the W key during play, a failed import quietly switches off autosave for the rest of the session, and Firefox may stall at "Click to play". A sixth bug matters more than any of them for the experience: **the horror event deck jams**. Simulated over ten nights, a cautious player gets exactly two major horror events in the whole session and **never sees the figure (0 of 150 runs)**, and a player who stays at the fire gets none at all. Behind the bugs sits the main design problem. Nights are survivable and fair, but they are static. The cold lasts **11.6 of every 20 minutes**, the fire keeps you comfortable only **within 3.4 m**, one mushroom fuels a whole night, and full gear (shelter, hide wrap, Fed buff) covers **about 93% of a night with no fire at all**. After the first dawn there is no next goal. The plan below is one "fix now" batch of bugs, then four batches in priority order (nights, performance, feel and visuals, audio), then what belongs to M2. File paths are relative to `/home/claude/biocrash/`.

## How this second review was done, and what it can't tell you

Three review passes read every file in `src/` and `index.html` as of 2026-11-20, plus the library source in `node_modules` (three 0.187, postprocessing 6.39.6, Rapier 0.21) wherever its behaviour mattered. `tsc --noEmit` passes and the production build succeeds (main code bundle 758.9 kB, Rapier physics 3.08 MB). The numbers in this report come from small throwaway simulations in `/tmp/bcsim/`. `thermal.py` copies the sky and survival maths, `horror.py`/`horror2.py` copy the horror director and run it 150-200 times per player type, `deco_count.ts` runs the real terrain and decoration generator for three seeds, and `deck.mjs` tests the event deck on its own. **Nothing was played in a browser or measured on a GPU.** Graphics memory figures are arithmetic, the Firefox stall comes from documentation, and the player types in the horror simulation are assumptions (for example, "a forager leaves the fire for 90 s every 4 minutes"). Treat the numbers as well-founded starting points, not measurements, and use one real Firefox session and one low-end laptop session to confirm the fix-now batch.

Items fixed since the first review are not repeated here except where a fix created a new problem. The earlier sound-design report's mix advice still stands.

## Fix now: six bugs that undo earlier work

Every item in this batch is small (a few lines to an afternoon), and each one either breaks a feature a previous batch added or can cost the player their progress or controls. Two of them come from batches that interact. Lazy audio loading (batch 2) breaks the horror deck (batch 4), and the remap menu (batch 6) breaks normal movement. That pattern argues for a handful of headless tests, described at the end of this section.

**Two flora materials compile into one shader.** The sway effect in `src/fx.ts:88-110` (`addSway`) builds the sway strength and bend into the shader code through a JavaScript closure. three.js decides whether two materials can share a compiled shader by comparing the *text* of that callback, which is identical for every call. So the glowing mushroom spots and the sprouts (`src/flora.ts:31-32`), which are otherwise configured identically, end up with the same shader program, and **whichever compiles first wins**. Either the glowing dots slide off the swaying caps, or the sprouts sway rigidly and their roots slide over the ground. The three.js tracker documents this trap: compiled programs are "cached based on the `onBeforeCompile` source code" ([three.js #19377](https://github.com/mrdoob/three.js/issues/19377)). The fix is one line per material: set `customProgramCacheKey` to return `sway:${amp}:${bend}` in `addSway`, and a fixed `'mist'` key in `addTerrainMist`. Which material wins depends on render order, so the bug may appear or vanish after unrelated scene changes. That is a reason to fix it rather than wait to see it.

**The Earth "memory" event fires twice, uncontrolled.** The `earth_*` recordings are 24 s long, are loaded lazily, and are evicted from memory after 60 s unused (`src/audio.ts:116-131, 517`). Memory events are minutes apart, so the sound is almost always cold. `play()` then returns nothing while it decodes, and the horror director (`src/horror.ts:335-345`) treats that as "couldn't play" and puts the card back. It immediately tries the next card, so **a second major event can fire in the same moment**. About 50 ms later, the audio system's queued retry plays the full 24 s memory anyway, with no caption, no cut-off, no static flash and no relax phase afterwards, and the real memory event can fire again 25-60 s later. The scariest-by-design event therefore bypasses all of batch 4's pacing. The fix is to pre-decode the `earth_*` files when the director enters its build phase (it knows seconds ahead which cards are eligible), and to never auto-replay a sound whose caller has already given up on it. Keep automatic retry only for ambient beds and drips.

**An abandoned key-remap prompt steals a movement key.** In `src/settings.ts:212-243`, clicking a key button enters "waiting for a key" mode, and nothing clears it when the player leaves the menu. If you click "Jump", then Back, then Play, the next key you press (say W) is rebound to Jump and removed from Forward. **The player can't walk forward, and the fix is in the menu they just left.** Clear the waiting state when settings close and on every state change, or ignore key capture unless the settings screen is visible.

**A failed import switches off autosave for the session.** `src/main.ts:385-389` stops the 10-second autosave timer *before* checking the import file. If the file is rejected (wrong file, another version, damaged chunk), the player sees an error message, but autosave never restarts. From then on, the world is saved only when the tab is hidden or closed, so a crash or power cut loses everything since the last tab switch. Move the `clearInterval` after a successful import. `importFile` already blocks saving while it writes (`src/save.ts:330`).

**Firefox may sit on "Click to play".** At startup the game waits for `navigator.storage.persist()` (`src/save.ts:171`, called from `main.ts:74`) before it wires the Play button (`main.ts:324`). Chrome and Safari answer this silently, but MDN notes that in Firefox "the user is notified with a UI popup that their permission is requested" ([MDN: Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Another web game hit exactly this: "In Firefox, `persist()` waits for the user's answer to a permission prompt" ([maple-survivors #148](https://github.com/itechify/maple-survivors/issues/148)). If the player misses or dismisses the prompt, the button does nothing and the game looks dead. Don't wait for the answer: call it fire-and-forget, ideally after the first successful save. Confidence is medium until tested on real Firefox.

**The horror deck jams, so cautious players lose the horror layer.** This is the most consequential bug in the build. When a card can't play (still locked for this night, or unease below its threshold), the director pushes it to the back of the deck (`src/horror.ts:113-119, 270-278`). The deck reshuffles only when it is empty, which now never happens, and played cards never return. The deck lives for the whole session, so the jam carries across nights and into caves. In simulation, a player who leaves the fire for 90 s every 4 minutes gets a memory on night 2 (64% of runs), a whisper on night 3 (99%), and **then nothing for nights 4-10**. The breath, voice, false-alarm and figure cards need higher unease than this player reaches, so they block the deck forever. A bold player still sees 2-3 events a night and meets the figure around night 4, which is good timing. Reloading the page resets the deck, which hides the bug during development: with a fresh deck each night, the same cautious player gets about 1.6 events a night from night 3. The fix is about ten lines. Draw only from cards that are eligible right now, track "played this cycle", reshuffle when every eligible card has played, never repeat the last card, and save the deck state with `HorrorSave`.

Several one-line bugs belong in the same session:

The last row matters more than its size suggests. The `sunset` warning is meant for players who are running out of time, but **the slowest players, who most need it, are exactly the ones still in the tutorial and so never see it.** Lines queued while the tutorial setting is off also play much later, out of context, when it is switched back on.

Finally, add the first tests. A headless run of `Horror.update` with a fake audio object whose `play()` returns nothing would have caught both the memory bug and the deck jam. A few pure-function tests for `sanitizeMeta` (a crafted `toString` item key, NaN versions, 60 packs) would protect the save layer, which is now robust against bad data. Its remaining weak points are about timing and locks, not validation.

## Batch 1: give the twelve-minute night something to do

Night 1 is fair. A new world starts with **8.2 minutes of warm daylight**, the core's chain (about 3 fiber, 6 stone, 4 stalkwood) is all within metres of the spawn, and a player who ignores everything freezes at about 11 minutes after one clear warning. The problem is what happens once the fire is lit. In simulation, unease at the fire stays at **0.00 on every night**, so a camper never sees a major event, only about 8 distant creature calls and 7 wreck groans a night, which is one minor sound every 45 seconds. The cold period fills **58% of real play time**, far more than Minecraft's "Day lasting ten minutes and night seven minutes" in a 20-minute cycle ([Minefort](https://minefort.com/blog/how-long-is-minecraft-day)), or Don't Starve's mid-summer night of 2 thirty-second segments in an 8-minute day ([Don't Starve Wiki](https://dontstarve.wiki.gg/wiki/Day-Night_Cycle)). And the fire's comfort zone is too small to do anything but stand there. Darkwood shows the risk: a reviewer describes nights where you "simply wait around for five minutes until something kicks down the door" ([Gamecritics](https://gamecritics.com/daniel-weissenberger/darkwood-review/)).

### The simulated night, in numbers

| Situation (from sunset, standing still) | Warmth runs out | Dead |
|---|---|---|
| Open air, no gear | 112 s | 145 s |
| Hide wrap + Fed | 231 s | 264 s |
| Shelter only | 291 s | 324 s |
| Shelter + wrap | 484 s | 518 s |
| Shelter + wrap + Fed | 605 s | 638 s |
| Respawned at midnight, open air | 126 s | 144 s |

Air is below comfort (12 °C) for **698 s of every 1,200 s** and bottoms out at −14 °C (`src/sky.ts` `DAY_LENGTH`, `src/survival.ts` TEMP). A full-strength fire keeps the air comfortable only **within 3.38 m**, shrinking to 2.10 m when fuel is under 60 s. The fire's light reaches 18 m (`src/campfire.ts`). Fuel is never a worry. The real generator places 44-48 ground stalkwood and 7-14 giant mushrooms within 40 m of spawn, and **each mushroom gives 8 stalkwood, about one night of fire**, so there are 15+ nights of fuel within 40 m even if half the mushrooms are culled. One Oomi kill (2 spear hits; it never flees) gives the bone needle, both hides for the wrap and 600 s of Fed, and two Tuko give the chitin spearhead, so **every M1 item can be finished on day 1**. The lamp's 240 s charge is always longer than any trip the cold allows, so it never limits anything. One quirk looks unintended: shelter pulls the air 85% of the way toward 5 °C at all hours (`src/survival.ts:65`), so **a cave at noon is 7.9 °C, colder than the open air**, and a player digging underground in daytime slowly freezes.

### What to change

Start with the death loop, because it is the one case where the numbers turn unfair. Respawning at the wreck at midnight gives 144 s to live, with every piece of stalkwood left in the dropped pack. A player whose fire is 80 m away can die, respawn, fail to reach pack and fire in time, and die again, **four or five times before dawn**. Respawn at the nearest lit fire the player built (fallback: the wreck), and keep 2 stalkwood out of the pack as a "fire kit". The alternative with a stronger horror fit comes from Darkwood: "If the player dies during the night, they will wake up in the next morning without receiving any reputation" ([Wikipedia: Darkwood](https://en.wikipedia.org/wiki/Darkwood)). In Biocrash terms, a night death skips to dawn, the pack stays where you fell, and the night doesn't count toward horror unlocks.

Next, the two numeric fixes: shelter should only ever warm (`t = max(t, lerp(t, 5, 0.85))`, or a constant 8-10 °C cave), and the fire's comfort radius should grow to about 5 m (heat constant 45 → ~60, or radius 8 → 10 m) so cooking, crafting and building at camp happen in comfort. If geared nights feel too easy after playtesting, soften the wrap from ×0.6 to ×0.75 and Fed from ×0.8 to ×0.85, which by the same formula cuts shelter + wrap + Fed from 605 s to about 455 s and keeps fire necessary. Shorten the lamp to about 150 s, or better, tie it to the horror (see below), so it becomes something the player plans around.

Then give the camp its own fear. From night 2, add a slowly rising unease floor (+0.05 per night survived, capped at 0.25, even at the fire) and a few low-threshold camp events: eyeshine at the edge of the firelight that's gone when the lamp touches it, footsteps circling just outside the 18 m light, a real gutter that burns 10-20 s of fuel, or a fresh trace found at dawn. Darkwood's light "rings the dinner bell" for its creatures ([Gamecritics](https://gamecritics.com/daniel-weissenberger/darkwood-review/)), which is the right model. At the same time, **thin the minor sounds**: about 15 creature and wreck sounds per night regardless of mood is the repetition Frictional regretted in Amnesia ("we repeat it too much", [Frictional Games](https://frictionalgames.blogspot.com/2012/09/amnesia-two-years-later.html?m=1)). Space them by unease (90-180 s when calm, 40-95 s when building) and cap wreck groans at about three a night. Add **one guaranteed, staged first figure sighting** on night 3-4 for players who haven't seen it yet, at fog distance and backlit by the wreck, then leave the rest random. Dredge's warning, "once you actually start seeing the monsters, they almost lose their impact" ([Game Developer](https://www.gamedeveloper.com/production/leveraging-the-unseen-to-turn-players-worst-fears-against-them-in-dredge)), argues against more than one.

Give nights their own activities: fire-side crafting that needs heat (cure hide, fire-harden the spear), and an optional **rest-by-fire fast-forward** at about 6× that needs fire plus shelter overhead and is woken by any major horror event. Don't Starve's tent lets players "sleep through dusk and night" at a hunger cost ([Don't Starve Wiki: Tent](https://dontstarve.fandom.com/wiki/Tent)), and Valheim's bed skips to morning with a dream on some sleeps ([Valheim Wiki: Sleeping](https://valheim.fandom.com/wiki/Sleeping)), a natural slot for a "nightmare" event. If that feels like too much new work, shortening the day from 20 to 16 minutes is the one-number alternative.

Finish with three small UX additions. Add a wrist **time-to-dark / time-to-dawn readout** ("dark in 3:10" after time 0.55), because the sky is the only clock outside the F3 debug view. Keep the **current goal pinned** as a small line under the vitals after its text fades. And use one compass waypoint for that goal, since the compass already supports extra marks (`src/main.ts:819-827`).

| Change | Where |
|---|---|
| Respawn at last lit fire + 2-stalkwood kit, or night death → dawn | `src/main.ts:862-880`, `src/survival.ts` |
| Shelter never colder than open air; fire comfort radius ~5 m | `src/survival.ts:65`, `src/campfire.ts` (HEAT_C / HEAT_RADIUS) |
| Night-scaled unease floor + low-threshold camp events; minor sounds scaled by unease | `src/horror.ts` |
| Staged first figure on night 3-4 if unseen | `src/horror.ts` |
| Heat crafting; rest-by-fire fast-forward with horror wake-up (or 16-min day) | `src/crafting.ts`, `src/campfire.ts`, `src/sky.ts` |
| Time-to-dark readout, pinned goal, goal waypoint | `src/tutorial.ts`, `src/main.ts`, `index.html` |
| Optional tuning: wrap 0.75, Fed 0.85, lamp ~150 s | `src/survival.ts`, `src/main.ts:597-602` |

## Batch 2: remove the remaining frame spikes and graphics-memory waste

The first review's big hitches are gone. The collider queue keeps the player's own chunk and its neighbours instant, builds the rest nearest-first, and holds old colliders until the next physics step, and **no way for the player to fall through the ground was found** (`src/terrain/world.ts:112-139`). What remains is a set of mid-sized costs, none measured in a browser, that hurt most on integrated graphics.

The largest unmeasured one is **the survival checks still using three.js raycasts** (`src/survival.ts:346-354`). Batch 2 moved only the aim rays to Rapier. Every 0.4 s, a 40 m "is there a roof?" ray and a 120 m "am I in shade?" ray test every triangle of every terrain mesh they pass. The first review measured 0.575 ms for a 7 m three.js ray against 0.0093 ms through Rapier, and a 120 m ray crosses far more terrain, so this is a regular spike 2.5 times a second. Use Rapier for the roof ray, and step along the sun direction comparing against the terrain height map for shade.

Next is **graphics memory spent twice on anti-aliasing**. The canvas is still created with `antialias: true` (`src/main.ts:46`) while the post-processing composer renders through its own 4× multisampled buffer (`src/fx.ts:23`). The pmndrs documentation recommends `antialias: false, stencil: false, depth: false` on the renderer for "an optimal post processing workflow" ([pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)). At 1080p with the 1.5× pixel ratio, the composer's buffers are about 225 MB and the unused canvas buffers add **about 150 MB more** (arithmetic, not measured), which integrated GPUs pay for in bandwidth every frame. Turn off the canvas anti-aliasing, use 2× multisampling on low settings, and while in that file set `effectPass.dithering = true`. The final 8-bit image still bands in near-black night gradients despite the higher-precision buffers before it.

**Auto-resolution misreads capped frame rates.** It lowers resolution whenever the frame rate is below 48 (`src/main.ts:944-950`), so on any device where the browser caps animation at 30 fps it shrinks to 50% while the GPU sits idle. iOS low-power mode roughly halves the frame rate ([daily.dev](https://daily.dev/posts/when-browsers-throttle-requestanimationframe-4w5w8xmy1)), and Chrome's Energy Saver limits animation effects ([How-To Geek](https://www.howtogeek.com/875326/chrome-energy-saver-mode/)). Each step also reallocates every render buffer, which is a hitch of its own. Drive the scaler from measured CPU frame time plus a GPU timer query, or detect a steady 33.3 ms frame with low work and leave resolution alone.

**Draw calls grow without limit with campfires.** Each fire is 14 separate meshes plus its own meat material, fires are never removed, every fire updates every frame, and the look-at check raycasts all of them 10 times a second (`src/campfire.ts:281-303`). Fifty fires is about **700 draw calls**, against a commonly cited ceiling of about 100 on mobile-class hardware ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips)). Merge each fire's stones and logs into one mesh, and skip updates and raycasts for distant fires. Creatures improved from about 12 meshes to 10 (Tuko) and 5 (Oomi), but each spawn still builds and merges its own geometry and materials on the main thread every 1.5 s while the population refills (`src/creatures.ts:26-43, 334-346`). Share geometry and materials per species and instance the legs.

Two robustness gaps belong here. "Start a new world" on the safe-start screen wipes the database without taking the single-tab lock (`src/save.ts:243-249`), so a second tab that failed to start can delete the first tab's terrain edits. Take the lock first and refuse if another tab holds it. And because three.js schedules the next frame *before* running the game loop, an error inside the loop repeats every frame with no recovery screen (`src/main.ts:838-975`). Wrap the loop body and show the safe-start box after a few consecutive failures.

Finally, one rendering cost is free to remove. Every lit pixel evaluates a hemisphere light, sun, moon, two campfire lights and the lamp, even at zero intensity. Simply hiding unused lights is not the answer, because it changes the light count three.js compiles into every shader and forces recompiles. But sun and moon are never both meaningful (`src/sky.ts:224, 228`), so **driving one directional light with whichever is up** removes one light from every pixel with no recompiles.

| Fix | Where |
|---|---|
| Survival roof/shade checks via Rapier and height map | `src/survival.ts:346-354` |
| Canvas `antialias: false`; MSAA 2 on low; `dithering = true` | `src/main.ts:46`, `src/fx.ts:23-32` |
| Auto-res based on frame time, not frame rate; detect vsync caps | `src/main.ts:944-950` |
| Merge each campfire's static meshes; skip far fires | `src/campfire.ts:281-303, 398-400` |
| Shared per-species creature geometry/materials; instanced legs | `src/creatures.ts:26-43, 320-346` |
| Lock-guarded `wipe`/`dumpRaw`; loop try/catch → safe-start | `src/save.ts:243-249`, `src/main.ts:838-975` |
| One directional light for sun or moon | `src/sky.ts:162-163, 224-228` |

## Batch 3: make the hands, the world and the night look finished

With the post stack in, the remaining visual problems are small and specific. Start with three bugs in the effects themselves. Chromatic aberration runs after bloom, so during glitches it replaces the red and blue channels with un-bloomed image and gives **green-tinted glow halos** (`src/fx.ts:32`); move it to the front of the effect list. The film grain uses an overlay blend that does nothing on near-black pixels, so **the unease grain vanishes exactly at night**; use an additive or screen blend at low strength. The mist shader calls `smoothstep` with its edges reversed (`src/fx.ts:77`), which the GLSL specification leaves undefined ("Results are undefined if edge0 ≥ edge1", [Khronos](https://registry.khronos.org/OpenGL-Refpages/es3/html/smoothstep.xhtml)); most drivers happen to cope, but write it as `1.0 - smoothstep(top - 7.0, top, y)`. The mist is also applied only to terrain, so stones, sprouts, creatures and packs stand crisp inside it. With post-processing off, the sky isn't tone-mapped while the fogged terrain is, which leaves a seam at the horizon; one `#include <tonemapping_fragment>` in `src/sky.ts` fixes it.

**The viewmodel is the most visible game-feel gap.** The held tool is a child of the world camera (`src/tools.ts:67`), so it shares the player's FOV slider, is lit by the world, and can poke into terrain and mushrooms. The standard three.js approach is to render the world, clear the depth buffer, then render the hands with their own camera ([three.js forum](https://discourse.threejs.org/t/rendering-a-gun-on-another-layer/80805)). Give the hands their own scene, a fixed FOV of roughly 55-65° (a common-practice estimate, not a sourced figure), copies of the sky and sun or moon light, and a lamp-side fill light when the lamp is on. Because bloom, vignette and tone mapping should apply to the arm too, the second pass has to live inside the composer as a second `RenderPass` that clears depth but not colour. Check that pmndrs supports this before building it. Add the small motions that are missing: a landing dip on the viewmodel, a slight sway that lags the mouse, and a 0.15-0.2 s raise animation when switching slots instead of the instant swap (`src/tools.ts:75-80`).

**Make harvesting visibly change the world.** Stalks don't change across their four harvests (`src/flora.ts:208-212`), and carcasses simply vanish (`src/creatures.ts:351`). Shrink the stalk in steps with a short squash, topple the cap on the last harvest with a spore puff and a thud, and leave a darker, stripped carcass that sinks or fades over a minute or two. The harvest counts are already saved, so the states rebuild on load. Replace instant campfire placement (`src/main.ts:642-650`) with a translucent ring-of-stones preview that turns red on steep ground or missing materials.

For the look, the cheapest wins come first. A **colour grade per time of day** costs almost nothing: pmndrs offers `LUT3DEffect` with `.cube` loaders, plus hue/saturation and brightness/contrast effects, and the AgX tone mapper, which "preserves colors well" ([DeepWiki: pmndrs colour grading](https://deepwiki.com/pmndrs/postprocessing/3.3-color-grading-and-tone-mapping)). Biocrash's pastel days are worth an A/B test against the current ACES. A **rim-light term** on creatures and flora (an extra emissive glow on edges facing away from the camera, warm by day and teal at night) separates silhouettes from fog at no extra pass cost. Sable's developers found fog "really, really key" and used distance-faded outlines and a moonlight shadow so players could read where they stood ([Game Developer: Sable](https://www.gamedeveloper.com/marketing/how-shedworks-refined-the-art-of-sable-in-pursuit-of-readability)). On the terrain, add two octaves of world-space noise (about 0.5 m and 4 m) that vary the colour by ±8-12%, plus height bands (pale spore dust high up, darker and wetter in hollows), inside the existing terrain shader hook. This gives most of what textures would, with no texture reads. Texture blending on three axes costs three texture reads per layer ([three.js forum: triplanar](https://discourse.threejs.org/t/tri-plannar-mapping-in-three-js/40335)), so leave it for a real art pass.

There are still **no shadows anywhere**. Add one shadowed directional light (sun by day, the large moon at night) on a 1,024 map covering ±25 m around the player, cast only by stalks, caps and creatures, refreshed every 2-3 frames, on Medium quality and above. Shadow memory grows with the square of the map size, and a point light would need six shadow renders, so fires never cast shadows ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips)). Package all of this into quality tiers, adding each layer only after checking its cost with a GPU timer:

| Tier | Settings |
|---|---|
| Low (integrated GPU) | Resolution 0.75; no shadow; no ambient occlusion; no MSAA (SMAA instead); grade and rim on |
| Medium | Resolution 1.0; one 1,024 shadow, hero objects only; MSAA 4 |
| High | Adds N8AO ambient occlusion at half resolution in Low mode; 2,048 shadow |

N8AO is the most expensive item. Its own notes put half resolution at "generally a 2x-4x speedup" with a fixed upsampling cost of "around 1ms", and transparent objects render twice ([N8AO](https://github.com/N8python/n8ao)), which matters for spores and flames. It stays High-only.

## Batch 4: let sound carry the horror and the hands

The audio system's structure is now right: the pause gain is separate from ducking, the reverb zones crossfade between open air and cave, and voices are capped. Three leftover bugs come first. Delayed horror sounds on the UI bus (the riser at 0.6 s, the gasp at 1.4 s, plus disrupt, receiver and static) **keep playing into the pause menu** (`src/horror.ts:306, 372`, `src/audio.ts:58`); route them through a bus under the pause gain. After the tab has been hidden for more than 60 s, the ambient beds' sound data is evicted. The bed loop then **re-enters its crossfade every frame** until decoding finishes, which makes the ambience dip audibly (`src/audio.ts:553-561`). Mark beds as in use while they play, and make the crossfade run once. And the Safari fallback from the first review is still missing: nothing checks `canPlayType`, and there is no AAC or MP3 set, so older Safari falls back to synthesized sound. iOS's "interrupted" audio state isn't handled either.

Then add the next layer, in this order. **Cheap obstruction** comes first. Once or twice a second, cast one Rapier ray from the player to each of the loudest positioned sounds (at most about six), and when terrain blocks it, smoothly lower that sound's existing low-pass filter, cut it by about 6 dB and raise its reverb send, so a call behind a hill sounds *around* the hill. A budget-occlusion guide suggests a 5,000 Hz low-pass and half volume when blocked, interpolated rather than switched, and warns against over-filtering into an "underwater" sound ([Wayline](https://www.wayline.io/blog/indie-game-audio-occlusion-budget)). For terrain, go deeper, to roughly 1-2 kHz. In caves, surface sounds should be obstructed by default. **Layered interaction sounds** come next: build each harvest, dig, hit and placement from a transient, a body and a tail, each picked from 3-6 variants with small random pitch, gain and timing offsets, plus a creak-and-fall on the final stalk harvest to match the topple animation. **Creature voices** should vary: give each creature a stable pitch offset (±3 semitones) and a filter tint, have a second creature answer 1-3 s later from another direction, and split calls into idle, alarmed, hurt and death sets. Alien: Isolation got a lot from one creature sound "varied with pitch and time manipulation", and kept its score restrained, "not afraid to use quiet and silence", because "the fear loses its impact if it's relentless" ([The Sound Architect](https://www.thesoundarchitect.co.uk/alienisolation/)). That supports **mostly silence for music**: keep the director's string swells and add only a sparse "safe" motif at a lit fire at dawn as a reward cue.

For the **wrist AI's voice**, don't synthesize speech while the game runs. Kokoro, a free speech model with Apache-licensed weights, runs in the browser, but even its smallest quantized version is an 86 MB download ([Xenova on Hugging Face](https://huggingface.co/posts/Xenova/503648859052804)), which is too heavy for a web game. Instead, render 20-60 lines offline with Kokoro on your PC (free, local), ship them as small Opus files, and process them live with a 300-3,400 Hz band-pass, light bit-crush and dropouts tied to the existing glitch value. That keeps the voice and its corruption under your control. Keeping the core text-only, with the voice reserved for rare corrupted lines, is an equally valid horror choice.

## What belongs to M2 and later

The single biggest M2 item is a **mid-game goal ladder**, because today the last line after dawn is the wreck's "Nobody has answered. Yet." and nothing follows. Comparable games show one next place or unlock at a time. Subnautica's repaired radio broadcasts "can lead you to new areas, new components, and generally progress the story", and the player respawns at the last habitat entered ([Subnautica Wiki](https://subnautica.fandom.com/wiki/Getting_Started)). Raft reveals each location's code at the previous one ([Raft Wiki](https://raft.fandom.com/wiki/Story)). Valheim's vegvisir "will add the location of the nearest Eikthyr Mystical Altar to your map", and the boss drop unlocks the pickaxe that opens mining ([Nodecraft](https://nodecraft.com/support/games/valheim/general/valheim-boss-guide-eikthyr)). A four-rung ladder fits Biocrash's recorded plans (scan-to-unlock, crafting chains no deeper than three, med-bay respawn, batteries and solar, glider then grapple, soft goals, no raids):

| Day | Goal the core gives | Unlocks |
|---|---|---|
| 2 | "Power the med bay": find 2 battery cells in wreck fragments 100-250 m out; build a solar patch | Med-bay respawn (full warmth, 75 hp) and a lamp charger |
| 3 | "Wake the scanner": scan Oomi, Tuko, sprouts, caps | Locked "???" recipes fill in; first unlock is a portable light, so nights gain mobility |
| 4 | "Boost the beacon": raise an antenna on cold high ground | Night-only signal fragments (a voice that shouldn't be there) and a bearing to biome 2 |
| 5+ | "Cross the ridge": biome 2's unique resource | Glider; grapple later |

Listening to the beacon only after dark makes the wreck a night destination and feeds the horror layer, and the crafting panel's "???" entries turn into a goal list.

Before M2 adds anything threatening, decide whether **the horror gets soft teeth**. The director's header says "Nothing here can hurt you", and in a world where creatures never attack, fear has no consequence. Comparable games make darkness cost something: Don't Starve's "Charlie will attack in complete darkness" ([Don't Starve Wiki](https://dontstarve.wiki.gg/wiki/Day-Night_Cycle)), and in Darkwood "each night the monsters also get a little bolder" ([Gamecritics](https://gamecritics.com/daniel-weissenberger/darkwood-review/)). SOMA, by contrast, offered harmlessness as a separate opt-in Safe Mode ("There is nothing to fear. You are always safe.", [Game Developer](https://www.gamedeveloper.com/design/-i-soma-i-dev-introducing-a-monster-optional-safe-mode-to-the-horror-game)). Biocrash can stay combat-free and still add costs: fuel lost when something passes the fire, cold spots, a lamp that dies near the figure, or a strike only in total darkness at very high unease. Today's harmless behaviour then becomes the peaceful mode.

The rest can wait. Engine work: a fixed 1/60 s physics step before thrown or falling objects (Rapier's own comment warns that "a timestep with large variations may cause instabilities"), and enabling `FIX_INTERNAL_EDGES` on terrain colliders, at some extra build cost, so rolling objects don't catch on chunk seams. Content and world: seasons or escalating nights (longer, colder every few days, as Don't Starve does), a wrist map of visited areas and pinged sites, spoken warmth warnings at 30 and 10, a raise-wrist vitals view, and difficulty presets for death (peaceful: no drop; normal: today; hard: drop tools too). Visuals: N8AO, grass cards from the existing decoration pass, a cloud layer, moon halos and phases, aurora on special nights, and water if the design adds it. Loose ends: pausing should stop flushing old colliders, because one can disappear a frame early after a dig and a quick Esc, a few-centimetre drop on resume. Save import should whitelist item keys and clamp campfire fuel to 600, keep the *newest* 50 packs and stop truncating long seeds. Hit damage should be locked at swing time rather than contact (scrolling to the spear mid-swing upgrades a knife hit). A keybind change should warn when it leaves crafting unbound, and remapped keys need their browser defaults blocked. Context-loss recovery with the composer is untested. Resource regrowth is not needed: with 15+ nights of fuel within 40 m, scarcity is not a lever until exploration needs a push.

## Conclusion

Both reviews found the same pattern. Each batch was correct on its own terms, and the bugs appeared where two batches met: lazy audio meeting the deck, the remap menu meeting the game loop, the import button meeting the autosave timer. The cheapest protection against more of these is not more code review. It is the three or four headless tests described above, run before each new batch, because M2 will multiply these crossings.

The design picture has also shifted. The first review asked whether nights were survivable and paced. They now are, so the open question is whether players will *want* to spend twelve minutes in them. Every simulated result points the same way: safety at the fire is total, fuel is unlimited and the horror only rewards leaving camp, so the game's tension is controlled by how bold the player chooses to be. Fixing the deck and adding a camp-side layer will tell you, in the first playtest, whether Biocrash's fear holds up when the player won't go looking for it. That answer should decide how sharp the M2 "soft teeth" need to be.
